# Repository workflow

## Branches

Use `<type>/<short-kebab-case-description>` in English. Allowed types are `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, and `chore`. Prefer a short description of the change, for example `feat/patient-transport` or `fix/reconnect-cleanup`.

## Commits

Use Conventional Commits: `<type>(<optional-scope>): <imperative summary>`. Use the branch types above. Write the summary in English, lowercase after the colon, without a final period, and keep the subject at or below 72 characters. Keep each commit focused. Add a body when the reason or migration impact needs explanation. Mark breaking changes with `!` and a `BREAKING CHANGE:` footer when applicable.

Use the repository user's configured Git identity. Never add Codex, an AI system, or another unrequested party as author or co-author. Do not add AI attribution trailers, comments, or PR text.

## Pull requests

Use the same format as a commit subject for the PR title. Fill in [.github/pull_request_template.md](../../.github/pull_request_template.md) in English: summary, validation, public-repository checks, and risks. Keep the description factual and mention any incomplete checks. Prefer a focused PR that can be reviewed as one change.

## Public repository safeguards

- License original project software under [GNU GPL version 3 only](../../LICENSE) (`GPL-3.0-only`). GPL permits commercial use of the code and requires covered derivative works to remain under GPL when distributed. Do not apply this license to third-party intellectual property. New contributions must be compatible with the project's license; use `GPL-3.0-only` in package metadata when added.
- Never commit secrets, API keys, tokens, credentials, private URLs, personal data, or real secret values in fixtures, logs, screenshots, docs, commit messages, or PRs. Use placeholders in examples; keep local environment files untracked.
- Review the diff and the staged file list before committing. If sensitive data was exposed, remove it from the change and rotate the affected credential; deleting it from the latest file alone is insufficient once published.
- Do not commit third-party sprites, audio, fonts, tilesets, or other external resources, including copies generated by an asset pipeline. Consume approved resources from an external source or from an ignored local cache. A URL or runtime fetch does not replace permission to use the resource: check usage terms, attribution, hotlinking rules, and availability first.
- Keep a small text manifest of approved external resource sources and required credits when assets are introduced. Avoid copying third-party license text unless its terms require it. Keep dependencies in package manifests and lockfiles rather than vendoring package contents.
